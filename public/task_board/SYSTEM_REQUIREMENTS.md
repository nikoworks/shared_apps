# TaskBoard 要件定義

更新日: 2026-06-22

## 1. 目的

TaskBoardは、NikoWorksの進行管理において、各メンバーの当日作業、未完了タスクの繰り越し、プロジェクト進行、確認事項を一元管理するためのアプリである。

スプレッドシートやChatworkだけでは見えにくかった次の問題を解決する。

- 誰が今日何をやるかが見えない
- 未完了タスクが埋もれる
- プロジェクトごとの進行状況が見えない
- Chatwork上のタスクが管理データとして残らない
- プロジェクト名やクライアント名の表記ゆれが増える
- 確認事項と作業タスクが混ざる

## 2. 基本方針

### 今日のタスクの定義

「今日のタスク」は、今日登録されたタスクではなく、今日中に終わらせるべきタスクである。

表示対象:

- 今日の日付で登録された未完了タスク
- 昨日以前に終わらず、作業日が今日へ移動された未完了タスク
- 未来日で登録され、その日になったタスク

完了済みタスクは通常表示から外すが、履歴として保持する。

未完了タスクが日を跨ぐ場合、新しいタスクレコードを日ごとに作成しない。既存タスクの作業日を今日へ移動し、元の日付は `originalDate` として保持する。

表示上は「6/7〜今日」のように、いつから繰り越されているかを示す。

### プロジェクトの定義

プロジェクトは、案件・納品物・月号・キャンペーンなど、進行を管理する単位である。

タスクは原則として必ずプロジェクトに紐付く。

未経験案件や未整理案件では、最初はフェーズなしでタスクを積み上げてもよい。

プロジェクトを削除する場合は、関連するタスクと、そのタスクまたはプロジェクトに紐付く確認・お願いも同時に削除する。

### フェーズの定義

フェーズは、プロジェクト内の工程である。

例:

- 企画
- 制作
- 確認
- 修正
- 提出
- 納品

フェーズは必須ではない。管理上必要になった時点で追加する。

### 確認の定義

確認は、進行に影響する判断・依頼・質問・共有である。

個人的な作業相談はTaskBoardの確認には含めない。

## 3. 利用者

| 利用者 | 主な役割 |
|---|---|
| 佐久間さん | 全体管理、プロジェクト整理、データ整理、最終確認 |
| 窓口担当 | 案件の進行責任、プロジェクト作成、納品日確認 |
| 発起人 | 新規案件の起点、プロジェクト作成 |
| メンバー | タスク入力、完了チェック、進行確認への対応 |

## 4. 主要機能

### タスク管理

必要機能:

- タスク登録
- 一括入力
- Chatwork取り込み
- 担当者別表示
- プロジェクト別表示
- 日付範囲表示
- 完了チェック
- 完了済み表示切替
- 未完了タスクの今日への移動
- 予定時間の0.25時間単位入力
- 備考入力
- 進行確認の登録
- 日を跨いだ未完了タスクを新規作成せず、既存タスクの作業日を更新する
- プロジェクト別タスク一覧では、繰り越し中の同一タスクを日ごとに重複表示しない

### Chatwork取り込み

TASK部屋から `#task` / `#ask` を含む投稿を取得する。

要件:

- 手動ボタンで取得できる
- 同じChatworkメッセージを二重取り込みしない
- 投稿者のChatworkアカウントIDから担当者を判定する
- 未登録メンバーの投稿は取り込まず警告する
- `,` と `/` の区切りに対応する
- 日付指定に対応する
- プロジェクト名不明は確認待ちにする
- 取得後は「全員、最新に更新してください」と案内する

### プロジェクト管理

必要機能:

- プロジェクト作成
- プロジェクト編集
- プロジェクト完了
- 完了プロジェクトの通常非表示
- クライアントで絞り込み
- 窓口担当で絞り込み
- 発起人の記録
- 納品日必須扱い
- 開始日管理
- 案件流入元の記録
- 案件流入元詳細の記録
- 定期案件名の管理
- プロジェクト種別管理
- フェーズ管理
- プロジェクトに紐付くタスク一覧表示
- プロジェクト削除時の関連タスク一括削除
- プロジェクト削除時の関連確認・お願い一括削除
- 制作テンプレートからのプロジェクト作成
- 納品日から逆算した仮スケジュール作成

プロジェクト作成権限の運用:

- 佐久間さん
- 窓口担当
- 発起人

上記以外のメンバーは、原則として既存プロジェクトを選ぶ。

### クライアント管理

現状、クライアントは独立テーブルではなく、プロジェクトの `clientName` として保存される。

必要機能:

- 既存クライアントのプルダウン選択
- 新規クライアント追加
- 表記ゆれの統合
- 統合時に、対象プロジェクトのクライアント名を一括置換

### データ整理

目的:

仕様変更やChatwork取り込みによって発生した不整合を、管理画面から整理する。

対象:

- 未紐付け・確認待ちタスク
- 仮プロジェクト
- クライアント名の表記ゆれ
- 繰り越し不整合
- フェーズ不整合
- 不足情報プロジェクト
- 重複タスク

要件:

- 重複タスクは、同じ担当者・同じ内容・同じ確認元または同じプロジェクト・同じ予定時間で、日付違いまたは複数存在するものを検出する
- 重複表示は1行にまとめる
- 正式プロジェクトへ紐付ける際、同じ重複グループもまとめて紐付けられる
- 削除ではなく、まずは統合・紐付け・アーカイブで整理する
- 繰り越し由来の重複は、最新の未完了タスクを残し、過去分を統合対象にする
- 完了済みタスクを含む重複は、内容確認ができるよう候補一覧を表示する
- 仮プロジェクトは、紐付くタスクが全て完了済みの場合、整理対象から非表示にする
- 紐付くタスクがない仮プロジェクトは、削除判断のため表示する

### テンプレート管理

目的:

制作案件や定期案件の入力負荷を下げ、納品日から逆算した仮スケジュールを作成する。

要件:

- テンプレートはフェーズ構成と標準タスクを持つ
- 標準タスクは、タスク名、フェーズ、種別、デフォルト担当、納品日からの営業日前、工数を持つ
- デフォルト担当が未設定の場合、プロジェクトの窓口担当を担当者にする
- プロジェクト作成時に、テンプレート選択と納品日入力から標準タスクを生成する
- 日付計算は土日祝を除いた営業日で逆算する
- テンプレート編集画面では、標準タスクを追加・変更・並び替え・削除できる
- 標準タスクの数が多い場合でも編集できるよう、ワイドモーダルとスクロールを備える

初期テンプレート例:

- プレゼントキャンペーン更新
- 広告運用
- 広告制作
- 記事制作
- Webページ制作
- 動画・SNS制作

### ガント

目的:

プロジェクト全体の流れを俯瞰し、クライアント別・定期案件別・担当者別に進行を確認する。

要件:

- クライアント別表示
- 定期案件別表示
- 窓口担当別表示
- 担当者別表示
- プロジェクト種別別表示
- 期間指定
- 日付ヘッダー固定
- 横スクロール
- プロジェクト単位のまとまり表示
- フェーズ行のグループ表示
- 遅れ気味のプロジェクト・フェーズの警告表示
- 納品日未設定の警告表示
- 完了プロジェクトの非表示

## 5. 画面要件

### タスク画面

表示内容:

- 担当者ごとのタスク
- 日付チップ
- 繰り越しラベル
- プロジェクト名
- クライアント名
- 予定時間
- 備考
- 確認ありラベル

並び順:

1. 古い繰り越しタスク
2. 昨日以前のタスク
3. 今日のタスク
4. 未来日のタスク

日付表示は、利用者が直感的にわかるように「今日」「昨日」「5日前」「6/12」などで表示する。

### プロジェクト画面

表示内容:

- クライアント名
- プロジェクト名
- 案件流入元
- 定期案件名
- 窓口担当
- 発起人
- 納品日
- 開始日
- フェーズ
- 紐付くタスク数
- 不足情報

フィルター:

- クライアント
- 窓口担当
- プロジェクト種別
- 案件流入元
- 進行状態

### 案件流入元管理

目的:

どのチャネルから来た案件が多いかを把握し、今後強化すべき営業・集客チャネルの判断材料にする。

プロジェクトごとに、案件流入元と流入元詳細を記録する。

案件流入元の選択肢:

- 自社開発
- LPからの問い合わせ
- 自社HPからの問い合わせ
- 既存クライアントからの紹介
- 代理店からの案件
- メディアレーダー
- 既存クライアントからの追加依頼
- 営業・直接提案
- その他

流入元詳細には、フォーム名、紹介元、媒体名、資料名、代理店名、営業経路など、後から分析に使える具体情報を残す。

### データ整理画面

表示内容:

- 未紐付けタスク数
- 仮プロジェクト数
- クライアント名数
- 繰り越し不整合数
- 不足情報プロジェクト数

操作:

- 未紐付けタスクを正式プロジェクトに紐付け
- 仮プロジェクトを正式プロジェクトへ統合
- タスクがない仮プロジェクトを削除
- 紐付くタスクが全て完了済みの仮プロジェクトを非表示
- クライアント表記ゆれを統合
- 不整合を修正
- プロジェクト・タスクを編集
- バックアップ取得
- 最新データ取得

## 6. データ要件

Supabase上では `taskboard_data` という1テーブルにJSONとして保存する。

JSON内の主要データ:

- `members`
- `projects`
- `tasks`
- `asks`
- `templates`
- `chatworkImports`
- `projectReviews`
- `meta`

詳細は `DATABASE_SCHEMA.md` を参照。

### タスクデータ

タスクは、日ごとの作業履歴ではなく、作業単位を表す。

主な項目:

- `date`: 現在の作業日
- `originalDate`: 繰り越し元の最初の作業日
- `completed`: 完了状態
- `projectId`: 紐付くプロジェクト
- `phaseId`: 紐付くフェーズ
- `taskType`: 作業、依頼、確認などの種別

未完了で日を跨いだ場合は、`date` を今日へ更新し、`originalDate` を保持する。日付ごとの複製タスクは作成しない。

### プロジェクトデータ

主な項目:

- `projectType`: 通常、定期、仮などの種別
- `isProvisional`: 仮プロジェクト判定
- `projectStatus`: 進行中、完了など
- `leadSource`: 案件流入元
- `leadSourceDetail`: 案件流入元詳細
- `ownerMemberId`: 窓口担当
- `createdByMemberId`: 発起人

プロジェクト削除時は、同じ `projectId` を持つタスクと確認・お願いも削除する。

### テンプレートデータ

主な項目:

- `phases`: フェーズ名の配列
- `tasks`: 標準タスクの配列
- `tasks[].offset`: 納品日からの営業日前
- `tasks[].hours`: 工数
- `tasks[].defaultMemberId`: デフォルト担当

## 7. 保存と同期

保存方式:

- 各操作後、ブラウザ内データを更新する
- Supabaseへ自動保存する
- 保存失敗時は警告を出す

同期方式:

- 他の人の画面は自動では即時更新されない
- 最新状態を見るには「最新に更新」を押す
- Chatwork取得後は、全員に更新を促す

将来的な自動同期:

- リアルタイム同期を導入する場合は、有料プランや実装コストを検討する
- 現時点では手動更新で運用する

## 8. 環境変数

Vercelに設定する環境変数:

| 変数名 | 内容 |
|---|---|
| `CHATWORK_API_TOKEN` | Chatwork APIトークン |
| `CHATWORK_ROOM_ID` | TASK部屋のルームID |
| `TASKBOARD_IMPORT_KEY` | 取り込み確認用キー |

Supabase接続情報は、公開してよいanon keyのみをフロント側で使う。

秘密情報はGitHubやアプリ画面に貼らない。

## 9. 現在の注意点

- 過去仕様で作成された仮プロジェクトが残っている
- プロジェクト未紐付けタスクが残っている
- クライアント名の表記ゆれがある
- 完了チェック後に、他端末では最新更新が必要
- 過去に日ごとに複製された繰り越しタスクが残っている場合がある
- データ整理画面で一度クリアな状態に整える必要がある
